# POS implementation plan

Review date: 2026-11-09. **Proposal only: do not implement until the project owner approves.** CR-07 additionally requires the explicitly requested client discussion. No migration, source change, or dependency installation is part of this review.

Evidence: [existing system](pos-existing-system-analysis.md), [gap table](pos-gap-analysis.md), [requirements](pos-client-change-requests.md), [decisions](pos-client-clarification-questions.md). All new filenames/model names/routes below are proposals, not existing functionality. Migration filenames are deliberately unassigned until the approved model changes are generated and reviewed after current `0021_stockbatch`.

## Architecture decision and compatibility

Extend the Django monolith and server-rendered frontend. Retain `Order` / `OrderItem` as the canonical supplied transaction and `Payment` as tender records. Do not introduce a second invoice sales ledger. Add proformas separately because they must have no stock or sales effect, unlike existing inactive unpaid orders. Add payment receipt identity to distinguish a collection event from a sale. Add structured units and purchasing models only where existing schema has no equivalent.

Expected focused new modules: `pos/services/numbering.py`, `inventory.py`, `sales.py`, `payments.py`, `proformas.py`, `purchases.py`, `pos/reporting.py`, and `pos/validators.py`. Only extract logic touched by these workflows; do not rewrite all views or add a REST framework. Existing views can remain compatibility wrappers and call the same services used by new forms.

Keep existing URL names, integer order numbers, legacy status values, payment method keys, template navigation, AJAX response keys, and print-agent JSON envelope. Add document lifecycle and settlement metadata separately from legacy `Order.status`; a partially paid invoice can remain legacy `unpaid` while displaying derived partial state in new screens. Legacy edit/pay/delete handlers must recognize issued documents and delegate/reject unsafe actions rather than bypass lifecycle services. Legacy draft and direct-sale behavior remains available except for explicitly approved integrity/policy changes.

## Proposed schema boundaries

| Boundary | Additive design | Historical handling |
|---|---|---|
| Numbering/audit | Transactional `DocumentSequence`, unique document numbers/request identities; actor/reason/reversal events | Preserve all existing numbers; new series cannot reuse deleted historical references where known |
| Supplied sale/invoice | Order kind/lifecycle, invoice number/issued date/due date if agreed; party FK and snapshot; immutable issue totals/line data | Leave legacy classification explicit; never turn all unpaid bills into issued invoices automatically |
| Customer/company | `Party` kind/contact fields with independent per-document snapshot | Existing customer_name retained verbatim; no automatic deduplication solely by name |
| Collection | `PaymentReceipt` header; Payment nullable receipt FK and reference/bank metadata; explicit payment reversal record | Existing rows remain supported without invented receipt references; reviewed legacy snapshot/backfill only |
| Proforma | `Proforma`, `ProformaItem`, protected unique converted-Order link and version/snapshot | New records only; retain source after conversion |
| Units | `Unit`, `ProductUnit`, nullable product defaults; entered unit/factor/base-quantity snapshots on transactional lines | Factor 1 for historical implicit quantities; unknown unit remains unknown |
| Inventory | `StockAllocation` linking order line, batch and quantity/cost; original movement/reversal/event links and unique posting keys | Reconciliation needed before allocations can be trusted; don't invent historical batch provenance |
| Purchasing | `Supplier`, `Purchase`, `PurchaseItem`, `GoodsReceipt` / lines, `SupplierPayment`, allocations, credits/adjustments | Preserve unknown supplier on legacy batches; approved opening balances are traceable dated entries |
| Local PO | `LocalPurchaseOrder` / lines, numbered lifecycle, references from goods receipts and purchases | New only; no impact on on-hand before actual receipt |

Use protected references/archiving for issued business records; product/supplier rename or deactivation cannot erase document content. Positive amounts/factors, unit uniqueness per product, nonnegative permitted quantities, unique conversion/posting identities, and allocation bounds need service validation plus feasible database constraints. Aggregate balance/receipt limits still require serialization; a field constraint alone cannot enforce cross-row totals.

## Stage 1 — Transaction, stock and audit foundations

- **Objective:** one auditable business posting per issue/return/settlement; reconcile FIFO before extending it.
- **Files/modules:** modify `pos/models.py`, `views.py` stock/payment/correction/delete functions, `admin.py`, `tests.py`, `building_pos/settings.py` if approved; add proposed `pos/services/{numbering,inventory,sales}.py`, `pos/validators.py`, and audited migrations after 0021. Update action forms in `templates/pos/{pos,order_view,reprint,unpaid_orders}.html` where policy changes affect actions.
- **Database:** additive sequence/audit/posting identity and batch-allocation tables/links. Reconcile product quantity, batch remaining totals and stock history on staging; retain an exception list for negative/unexplained legacy stock. Do not manufacture old cost layers or silently normalize debt/stock. Start allocations prospectively where historical provenance cannot be recovered.
- **Backend:** move touched posting rules into atomic services; lock parent then products/batches in stable order; recompute totals/state inside transaction. Recheck status in both checkout paths. Persist final FIFO consumption at issue, not merely cart preview; store cost snapshots from actual allocations. Restore original layers or explicit documented return layers on returns/reversals. Give GET actions read-only semantics by adding POST transitions without removing existing URL identities. Guard admin edits and issued-document deletion/corrections under approved policy; retain legacy operations only where safe.
- **Frontend/API:** reuse current forms/messages; add conflict/shortage handling, confirmation of authorized reversals and reasons. Preserve success/error JSON keys and use additive conflict details/HTTP 409 where appropriate. Server idempotency handles retried POSTs and stale forms, including legacy clients lacking a new request key through a locked single-state transition.
- **Business rules:** stock post and canonical issue are indivisible; repeat issue returns existing result. Payment cannot be duplicated by parallel checkout. No global assumption that `select_for_update()` makes SQLite row locks effective. If keeping SQLite, prove explicit supported write serialization with bounded conflict handling; otherwise propose and approve a transactional database/driver change before implementation. No new database dependency is authorized by this report.
- **Dependencies:** Stage 0; C8–C11/I10–I11 for relevant policy.
- **Tests:** independent concurrent connections/processes on the actual supported database, duplicate issue/pay requests, totals edited between preview and commit, deadlock/lock retries, failure rollback, FIFO return/reopen/correction conservation, unauthorized operations/admin, number races and no stock change on reprint. Existing paid-edit/delete/negative-stock tests must be updated only for approved policy changes, not discarded to hide regressions.
- **Acceptance:** repeated/parallel issue posts one movement set; duplicate checkout cannot add money twice; product/batch quantities reconcile for new transactions; reversals retain links/actors; rollback leaves no orphan events; no existing authorized API keys/routes disappear.
- **Risk/mitigation:** existing mutable corrections and SQLite semantics are high risk. Ship this foundation before credit/procurement behavior; isolate any approved database transition with backup/restore and reconciliation.

Unchanged historical tender amounts/change/dates. Add cheque choices via reviewed additive migration; no gateway tables.
- **Backend:** shared method definitions/validation; amount is finite, within decimal precision, positive as applicable. Decide precision before changing decimal columns. Seed only requested unit vocabulary; factor-1 legacy compatibility does not assert that legacy stock was PCS.
- **Backend:** normalize stock operations once at service boundary; sales price per selected unit and FIFO cost per base unit; keep fractional validation and rounding explicit. Revalidate factors and quantities at posting. Changing a factor affects new lines only; base-unit change on stocked products requires controlled reviewed conversion. - **Frontend/API:** unit selectors with explanatory quantity/price labels and base-stock preview; per-product conversion maintenance; unit metadata added to JSON without removing existing fields. - **Acceptance:** five requested unit labels available; purchase and sale units may differ; document reprint and return use original factor/price; legacy values unchanged; normalized on-hand and batch totals reconcile.
- **Risk/mitigation:** ambiguous legacy units or insufficient precision. Disable conversion for unresolved products; do not infer mappings from name/box or round silently.

## Migration and rollout procedure for approved work

1. Back up and restore production-equivalent data to staging; capture row counts, sums and exception records. Never trial data migrations on the only live database.
2. Add nullable fields/tables first; old code/records can coexist. Do not modify 0001–0021 or rerun historical cost/stock backfills.
3. Backfill only deterministic fields in bounded, restartable operations. Preserve old names/prices/amounts/dates. Do not infer customer identity, supplier provenance, unit factor or issue status from similar names. Review ambiguous records explicitly.
4. Deploy compatible readers/writers; prevent older writers from bypassing new issued-document rules. Test both old form payloads and new workflows before enabling them for users.
5. Add strict constraints after audit confirms data meets them; preserve original IDs and document numbers. Reconcile stock, batch costs, receivables, payables, collections and profit against reviewed baselines.
6. Enable approved workflows in staging, accept documents on actual printers, then perform controlled production release and reconciliation. In-flight paid corrections and claimed print jobs need explicit handling during cutover.
7. Roll back code only if it still understands new persisted events. Never drop new financial tables or reverse posted events destructively as a rollback. Prefer disabling new entry points and retaining readable history; any compensating corrections are audited transactions. Verify restore on staging before release.
